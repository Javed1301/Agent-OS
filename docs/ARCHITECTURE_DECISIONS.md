# Architecture Decision Records (ADRs) — Agent Workspace

This document records the key technical and architectural decisions made throughout the development of **Agent Workspace (Agent OS)**.

---

## ADR-001 — Manifest-Based Agent Discovery (`agent.yaml`)

### Status
Accepted

### Context
Heterogeneous AI agents built on CrewAI, LangChain, RAG, or custom Python scripts had hardcoded initialization scripts and required manually configuring python entrypoints and gateway routes. This prevented modular agent addition and plugin reuse.

### Options Considered
1. **Hardcoded Gateway Registrations**: Register each agent programmatically in TypeScript route files.
2. **Database-Driven Registration**: Store agent metadata in a SQL/NoSQL database table.
3. **Manifest-Based Discovery (`agent.yaml`)**: Define agent metadata, entrypoint, required environment variables, working directory, and input schema in a declarative `agent.yaml` file in each agent's directory.

### Decision
Adopt manifest-based agent discovery (`agent.yaml`). The gateway automatically scans `agents/*/agent.yaml` and `external-agents/*/agent.yaml` at startup.

### Why
Decouples agent definitions from gateway source code. Allows developers to register a new agent simply by dropping a directory with an `agent.yaml` manifest into the workspace—zero gateway code changes required.

### Consequences
- Adding an agent requires creating `agent.yaml`.
- Gateway requires a scanner service (`RegistryService`).

### Current Implementation
- `apps/gateway/src/services/registry.service.ts`
- `docs/agent-packaging-standard.md`

## ADR-002 — In-Memory Registry Catalog & Hot-Reload

### Status
Accepted

### Context
Accessing agent metadata on every REST call (listing agents, rendering UI schemas, running health checks) requires fast access without disk I/O bottlenecks.

### Options Considered
1. **Re-parse YAML on every HTTP Request**: High filesystem read latency.
2. **Database Caching**: Introduces external database dependency for MVP.
3. **In-Memory Registry Catalog with Hot-Reload API**: Parse manifests once on boot into an in-memory array `_agents`, with a `POST /api/agents/reload` endpoint for hot-reloading.

### Decision
Maintain an in-memory catalog loaded at boot, with hot-reload capabilities.

### Why
Provides sub-millisecond API response times (`<10ms` for agent listing) while retaining the flexibility to register new agents on the fly via `POST /api/agents/reload`.

### Current Implementation
- `apps/gateway/src/services/registry.service.ts` (`load()`, `reload()`, `listAgents()`)

## ADR-003 — Adapter Abstraction Layer (`AgentAdapter`)

### Status
Accepted

### Context
Agents run under different environments: local CPython scripts (`scripts/runner.py`), CrewAI crews, LangChain RAG pipelines, or external HTTP microservices (FastAPI). Coupling the execution engine directly to process spawning would prevent supporting REST microservices or future containerized runtimes.

### Options Considered
1. **Direct Subprocess Spawning Only**: Hardcode `child_process.spawn()` in execution routes.
2. **Polymorphic Adapter Interface**: Define a generic `AgentAdapter` interface with standard lifecycle methods (`execute`, `health`, `cancel`).

### Decision
Implement the `AgentAdapter` abstraction layer.

```typescript
export interface AgentAdapter {
  execute(ctx: AdapterContext): AdapterHandle;
  health(agent: AgentDefinition): Promise<HealthResult>;
  cancel?(executionId: string): Promise<void>;
}
```

### Why
Enables seamless execution of both local Python subprocesses (`PythonSubprocessAdapter`) and HTTP microservices (`RestApiAdapter`) through a single unified API endpoint (`POST /api/agents/:id/execute`).

### Current Implementation
- `apps/gateway/src/adapters/base.ts`
- `apps/gateway/src/adapters/python.ts`
- `apps/gateway/src/adapters/rest.ts`

## ADR-004 — Per-Execution Directory Sandboxing (`data/executions/<id>/`)

### Status
Accepted

### Context
Running concurrent agents or re-running agents multiple times in a shared directory risks file clobbering, race conditions, corrupted outputs, and difficult post-mortem debugging.

### Options Considered
1. **Shared Workspace Outputs**: Output files written directly to agent source directories.
2. **Isolated Per-Execution Folders**: Assign every execution a unique ID (`exec_YYYYMMDD_XXXXXXXX`) and dedicated workspace folder `data/executions/<id>/`.

### Decision
Adopt strict per-execution directory sandboxing.

```
data/executions/exec_20260812_a1b2c3d4/
├── input.json      ← written by gateway prior to execution
├── output.json     ← final ExecutionRecord & result payload
├── logs.txt        ← combined real-time stdout/stderr/gateway logs
└── artifacts/      ← output files generated by agent
```

### Why
Guarantees 100% reproducibility, zero cross-execution file collisions, clean artifact collection, and effortless post-execution debugging.

### Current Implementation
- `apps/gateway/src/services/store.service.ts`
- `apps/gateway/src/services/execution.service.ts`

## ADR-005 — Working-Directory Mutex Locking (`usesWdLock`)

### Status
Accepted

### Context
Certain legacy Python agents or CrewAI tools write intermediate analysis to hardcoded relative filenames in their source working directory (e.g. `task_outputs/report.md`). Concurrent runs of such agents would overwrite each other's files mid-execution.

### Options Considered
1. **Refactor All Agent Python Source Code**: Prohibit hardcoded relative output paths across all imported agents.
2. **Working-Directory Mutex Queue**: Allow agents to specify `usesWdLock: true` in `agent.yaml`. When enabled, the gateway serializes concurrent executions for that working directory using an in-memory promise lock (`wdLocks`).

### Decision
Implement working-directory mutex locking for agents that require local disk serialization.

### Why
Preserves compatibility with third-party or imported agent code without requiring modifications to the agent's internal Python scripts.

### Current Implementation
- `apps/gateway/src/services/execution.service.ts` (`acquireWdLock()`)

## ADR-006 — Server-Sent Events (SSE) Streaming & Replay Buffer

### Status
Accepted

### Context
AI agents take 10 to 60 seconds to run. Blocking HTTP responses leave users with a spinning screen. The platform required real-time terminal output streaming.

### Options Considered
1. **WebSockets (Two-Way)**: Full bi-directional protocol.
2. **Long Polling**: Frequent HTTP GET requests polling log files.
3. **Server-Sent Events (SSE) (One-Way Streaming)**: Standard HTTP streaming protocol.

### Decision
Choose Server-Sent Events (SSE) for execution streaming (`GET /api/executions/:id/stream`).

### Why
- Agent log streaming is inherently **one-way** (server $\rightarrow$ client).
- SSE runs over standard HTTP/1.1 and HTTP/2, requiring no custom WebSocket handshake or proxy configuration.
- Combined with an in-memory `eventLog` buffer on `ActiveExecution`, late-connecting web UI clients immediately receive all historical log lines upon connection.

### Current Implementation
- `apps/gateway/src/services/execution.service.ts` (`streamExecution()`, `broadcast()`)
- `docs/api-contract.md`

## ADR-007 — Content-Addressed Python Runtime Management with `uv`

### Status
Accepted

### Context
Traditional Python virtual environments (`.venv`) created per agent cause massive disk duplication (1.5 GB–2.5 GB per CrewAI agent) and 2–5 minute setup delays. Global Python environments cause dependency conflicts between agents.

### Options Considered
1. **Single Global Virtualenv**: High risk of package dependency conflicts (e.g., CrewAI vs LangChain version mismatches).
2. **Standalone `.venv` Per Agent**: Heavy disk footprint (30–50 GB for 20 agents) and slow setup times.
3. **Content-Addressed Shared `uv` Runtimes**: Use Astral's Rust-based `uv` package manager. Hash the agent's Python version and normalized dependency file (`uv.lock`, `pyproject.toml`, `requirements.txt`) using SHA-256 (16-char hex). Store runtimes in `runtimes/py311/<hash>/.venv`.

### Decision
Adopt content-addressed shared `uv` runtimes.

### Why
- Agents with identical dependencies automatically share the same virtual environment instantly (0 ms setup).
- `uv`'s global package cache (`uv-cache`) hardlinks wheels, saving 80% to 90% disk space across different runtimes.
- Environment creation via `uv` takes seconds instead of minutes.

### Current Implementation
- `apps/gateway/src/services/runtime.service.ts`
- `docs/runtime-architecture.md`

## ADR-008 — File-Based Runtime Build Locking (`.lock`)

### Status
Accepted

### Context
When multiple agents with identical dependencies are triggered or imported simultaneously, concurrent `uv venv` or `uv pip install` processes could collide in the same target runtime directory (`runtimes/py311/<hash>/`), causing file corruption.

### Options Considered
1. **In-Memory Promises Only**: Works only within a single process; fails across multi-process or worker setups.
2. **File-Based Build Locks (`.lock`)**: Write a lockfile (`runtimes/py311/<hash>.lock`) containing process ID and creation timestamp. Waiting processes poll every 1,000 ms with a 5-minute timeout and stale lock recovery.

### Decision
Implement file-based runtime build locking.

### Why
Ensures atomic runtime creation across process restarts, concurrent requests, and container environments.

### Current Implementation
- `apps/gateway/src/services/runtime.service.ts` (`acquireBuildLock()`)

## ADR-009 — Automated Runtime Garbage Collection

### Status
Accepted

### Context
Managed virtual environments can accumulate over time as imported agents are updated or removed, taking up host storage.

### Options Considered
1. **Manual Cleanup**: Rely on developers to delete folders.
2. **Automated GC Endpoint (`POST /api/runtimes/gc`)**: Enforce precedence collection rules:
   1. Delete orphaned runtimes (`agentCount == 0`).
   2. Delete runtimes unused for > 30 days.
   3. Enforce a 10 GB disk quota using Least Recently Used (LRU) eviction.
   4. Protect the **3 most recently used runtimes** from deletion.

### Decision
Implement automated runtime garbage collection with protected MRU runtimes.

### Why
Keeps disk usage bounded under host quotas while ensuring active and recently used environments are never disrupted.

### Current Implementation
- `apps/gateway/src/services/runtime.service.ts` (`runGC()`)

## ADR-010 — Process-Tree Cancellation (`tree-kill`)

### Status
Accepted

### Context
Cancelling a running Python agent via standard Node.js `process.kill()` terminates only the parent wrapper process. Background child processes spawned by CrewAI, LangChain, or CPython remain active, consuming 100% CPU and holding file locks.

### Options Considered
1. **Standard `process.kill()`**: Leaves orphaned subprocesses.
2. **Process-Tree Killing (`tree-kill`)**: Recursively inspect operating system process trees (using `taskkill /F /T` on Windows or `kill -9` on POSIX) to kill parent, child, and grandchild PIDs.

### Decision
Use process-tree killing for process cancellation.

### Why
Guarantees clean process cleanup across Windows, Linux, and containerized deployments.

### Current Implementation
- `apps/gateway/src/services/execution.service.ts` (`cancel()`)
- `apps/gateway/src/services/process.service.ts`

## ADR-011 — Encrypted Local Secrets Vault (AES-256-GCM) & Dynamic Subprocess Injection

### Status
Accepted

### Context
AI agents require private API credentials (`GEMINI_API_KEY`, `OPENROUTER_API_KEY`, etc.). Storing keys in plain text files or exposing them in API responses risks credential leakage.

### Options Considered
1. **Plain Text `.env` Files Only**: Risk of checking secrets into Git or exposing them in raw logs.
2. **Cloud Key Management Service (KMS)**: Violates local-first offline philosophy.
3. **Local Encrypted Vault (AES-256-GCM)**: Encrypt credentials on disk (`data/secrets/vault.json`). Decrypt keys strictly in memory at subprocess spawn time (`buildSpawnEnv()`). Automatically redact secret values from real-time log streams.

### Decision
Implement a local encrypted secrets vault using AES-256-GCM with dynamic in-memory injection.

### Why
Maintains 100% offline local privacy while preventing credential leakage in logs, disk persistence, or REST responses.

### Current Implementation
- `apps/gateway/src/services/secrets.service.ts`
- `apps/gateway/src/services/health.service.ts` (`buildSpawnEnv()`)

## ADR-012 — Declarative Multi-Agent Workflow Engine & Context Interpolation

### Status
Accepted

### Context
Orchestrating multi-agent tasks (e.g., Planner $\rightarrow$ Code Generator $\rightarrow$ Code Reviewer) required custom code for each agent chain.

### Options Considered
1. **Custom Hardcoded Script Chains**: Code each workflow in TypeScript.
2. **Declarative YAML Workflow Engine**: Define workflows in `workflows/*.yaml` with step definitions and template interpolation (`${input.prompt}`, `${steps.plan.output.plan}`, `${steps.plan.artifacts}`).

### Decision
Build a declarative YAML workflow engine with dynamic template resolution.

### Why
Allows creating complex multi-agent pipelines declaratively without writing custom orchestration code.

### Current Implementation
- `apps/gateway/src/workflows/engine.ts`
- `apps/gateway/src/workflows/parser.ts`
- `apps/gateway/src/workflows/resolver.ts`
- `docs/workflows.md`

## ADR-013 — Monorepo Architecture (npm Workspaces)

### Status
Accepted

### Context
Developing backend gateway APIs and Next.js frontend UI components in separate repositories caused version drift and code duplication.

### Options Considered
1. **Separate Repositories**: `agent-gateway` and `agent-dashboard`.
2. **Single Monorepo via npm Workspaces**:
   - `apps/gateway`: Express API backend (Port 8080/4000)
   - `apps/dashboard`: Next.js 15 App Router frontend (Port 3000)
   - `packages/`: Shared TypeScript types and utilities

### Decision
Adopt a monorepo structure with npm workspaces.

### Why
Simplifies dependency management (`npm install` at root), enables shared TypeScript types, and provides single-command development (`npm run dev`).

### Current Implementation
- `package.json` (`workspaces: ["apps/*", "packages/*"]`)

## ADR-014 — Filesystem-Based Persistence Strategy (Zero-DB MVP)

### Status
Accepted

### Context
Storing execution records, logs, and workflow states in an external database (PostgreSQL, SQLite, MongoDB) adds installation and setup overhead for local developers.

### Options Considered
1. **Relational Database (PostgreSQL / SQLite)**: Requires database setup, migrations, or native C bindings (`better-sqlite3`).
2. **Filesystem Persistence**: Write JSON files per execution (`data/executions/<id>/output.json`), append-only text logs (`logs.txt`), and a lightweight global index file (`data/executions/index.json`).

### Decision
Use filesystem-based persistence with lightweight JSON indexing.

### Why
Zero external dependencies, 100% human-readable execution history, easy manual inspection, and effortless backup/deletion.

### Current Implementation
- `apps/gateway/src/services/store.service.ts`

## ADR-015 — Docker Compose Hybrid Local/Container Deployment Model

### Status
Accepted

### Context
Users require both lightweight local development and containerized server deployments.

### Options Considered
1. **Bare-Metal Only**: Cannot run on isolated cloud containers.
2. **Docker-Only**: Requires Docker daemon for local dev.
3. **Hybrid Architecture**: Support both bare-metal (`npm run dev`) and `docker-compose.yml`. Use environment variables (`DOCKER_ENV=true`, `WORKSPACE_ROOT=/app`) to dynamically adjust path resolution and storage roots (`/app/runtimes` vs `~/.agent-os/runtimes`).

### Decision
Implement a hybrid architecture supporting bare-metal local development and Docker Compose containerization.

### Why
Provides zero-friction local development for developers while allowing one-command containerized production deployments (`docker compose up`).

### Current Implementation
- `docker-compose.yml`
- `apps/gateway/Dockerfile`
- `apps/dashboard/Dockerfile`
